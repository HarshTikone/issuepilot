# Security and operational boundaries

Issue text, source files and model output are untrusted. This implementation narrows their authority, but it is a portfolio service for a dedicated VPS, not a claim of production-grade containment against every adversarial input.

## Credential and execution separation

The trusted Python supervisor has the GitHub token and Docker access. The GitHub token is scoped to one repository, with Contents read and Issues read/write. It is never forwarded to the task container, put in task files, or interpolated into a shell command.

The task container receives a model API key through Docker's environment, plus a read-only directory containing only an issue snapshot and selected source text. Model keys are therefore accessible inside the agent's runtime; use a separate limited key. Exact known-secret and token-pattern checks block obvious leakage in reports, but these checks are not a complete data-loss prevention system and do not detect every encoded transformation.

The container runs as UID 10000, with a read-only root filesystem, dropped Linux capabilities, no-new-privileges, CPU/memory/process limits and writable in-memory profile/temp directories. It receives no host home directory, supervisor data directory, SSH keys, Docker socket or GitHub token. Only the `file` toolset is requested; source code is never executed. Safe mode disables custom rules, hooks, plugins and MCP configuration for this invocation. These controls depend on the selected image preserving the expected CLI semantics; the live smoke check is mandatory.

The supervisor's membership in the Docker group is powerful enough to control the host. Treat the supervisor and Docker daemon as trusted, keep their code/configuration root-owned, and use a dedicated VPS with no unrelated credentials or workloads. A future hardened deployment can use a separate rootless runner host/API.

## Input and output controls

- An issue must be open, written by an explicitly allowlisted author and carry the work label. Outsider issues are ignored even if labelled.
- Source files are chosen in configuration, fetched as data from a single immutable GitHub commit, and limited by path/type/byte caps. Hidden and obvious key files are rejected. Curate this list; filenames alone cannot establish absence of secrets.
- Repository instructions are not executed or automatically loaded. The prompt treats file and issue contents as data.
- Reports require exact JSON fields, known source files, valid line ranges and bounded text/list sizes. Schema failures are visible job failures.
- Model-generated text is escaped before it enters GitHub Markdown, and mentions are disrupted. Source links are generated by the supervisor.
- Reports explicitly identify static analysis and proposed tests. A valid citation range does not prove the finding is true.
- Issue state, label, author and text are rechecked before publication. A withdrawal or text edit cancels stale work.

## Reliability boundaries

The per-data-directory OS lock permits one active supervisor. SQLite persists queue states and the prepared report. Jobs are unique by repository and issue number. A crash after report creation can resume publication without another model call.

The comment marker is accepted only on comments owned by the authenticated GitHub actor. This prevents another account from suppressing a task by copying the marker. After an ambiguous POST, the worker searches for that marker before posting again. GitHub does not expose an atomic comment idempotency key; unusual visibility delays can still cause duplicates.

The rolling model-start cap counts attempted starts conservatively and survives restarts. It is not a monetary cap. Wall-clock limits terminate task containers but cannot reverse provider charges already incurred. Configure provider-side limits and review actual usage.

## Network and storage

No public HTTP listener is needed. Health/readiness bind only to `127.0.0.1`. The supervisor needs outbound HTTPS to GitHub; the agent needs outbound inference access. This version does not implement provider-domain egress filtering.

Private SQLite records contain issue text and reports. Abrupt host termination can leave curated source input directories until reviewed and removed. Keep database backups private and choose a retention policy for your own repository. Do not publish raw service environment files, provider keys, unredacted transcripts or SSH private keys.

## Deferred controls

GitHub App short-lived tokens, rootless remote execution, network egress allowlists, audit/retention automation, provider usage ingestion, formal schema migration support and independent patch/test execution are future work. Auto-merge and production deployment are outside this version's authority.
